# Formal report bundle v1

`fmctl` execution already records the exact `EffectiveResourcePolicy` that
controlled the child process. This report layer renders that same envelope into
four deterministic, secret-free formats without recomputing policy from the
manifest.

## Formats

1. **JUnit XML** — one suite and one operation test case. Stable properties
   flatten every requested, default, maximum, effective, inherited, and clamped
   resource-policy field.
2. **SARIF 2.1.0** — one run with the full resource-policy object in run
   properties and content-free timeout/failure results.
3. **Artifact manifest JSON** — operation identity, status, sorted artifact basenames,
   and the exact resource-policy envelope. Absolute runner/user directories are removed.
4. **Provenance JSON** — operation/result identity, sanitized command identity,
   an extensible input-hash map, and the exact resource-policy envelope.

The aggregate `ReportBundle` includes all four renderings and has
`schema_version = 1`. The artifact and provenance schemas are identified as
`fm.artifacts.v1` and `fm.provenance.v1`.

## Determinism

Identical `CommandOutcome` values produce byte-identical JSON and XML. JSON uses
stable struct field order and recursively ordered maps. JUnit properties are
stored in a `BTreeMap` and XML attributes are escaped deterministically. Artifact
entries are sorted by kind.

No wall-clock timestamp is generated by the renderer. Duration comes from the
recorded outcome; input hashes remain absent until the planner exposes verified
manifest/specification hashes.

## Secret and content boundary

The reports deliberately omit:

- environment keys and values;
- raw command arguments;
- stdout and stderr contents;
- failure text;
- adapter mismatch payloads;
- specification/source contents; and
- generated trace payloads; and
- absolute artifact directory prefixes.

Provenance records only the executable basename and argument count. Failure and
timeout reports use fixed content-free messages. The exact resource policy is
safe to include because it contains numeric limits and field names, not secrets
or source data.

## Result mapping

| Outcome | JUnit | SARIF | JSON status |
| --- | --- | --- | --- |
| success | no failure element | no result finding | `passed` |
| timeout | `timeout` failure | `fmctl.timeout` error | `timed_out` |
| other failure | `command_failure` failure | `fmctl.command_failed` error | `failed` |

These formats describe execution evidence only. A passing report does not expand
what the selected model, bounds, implementation adapter, or assumptions prove.

## Utility

The non-published `fm-report-bundle` binary reads one regular `result.json`,
bounds the input to 64 MiB with a ceiling-plus-one read, and emits one selected
format to stdout:

```sh
cargo run --manifest-path tools/fmctl/Cargo.toml \
  --bin fm-report-bundle -- \
  .formal-artifacts/result.json --format bundle
```

Supported formats are `bundle`, `junit`, `sarif`, `artifact-manifest`, and
`provenance`. Diagnostics go to stderr.

## Remaining integration

A follow-up must publish the four files atomically beside `result.json` for every
CLI and JSON-RPC execution path, add explicit profile selection, and include
verified manifest/specification hashes when the planner exposes them.
